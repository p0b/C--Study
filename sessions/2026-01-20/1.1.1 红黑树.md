**这里为什么要用define而不是用typedef，为什么要用RBTREE_ENTRY,其中（name，type）代表什么**

+ **用 define 而不是 typedef**，因为你需要“带参数生成类型”的能力，`typedef` 不能参数化，宏可以按 `type` 生成正确的指针字段。
+ **用 RBTREE_ENTRY** 是为了把红黑树链接域抽象成可复用模板，减少重复、统一布局、降低类型写错概率。
+ **(name, type) 中**：`type` 决定指针指向的节点类型；`name` 是生成的 `struct` 标签名，可用于避免冲突，也可留空生成匿名 struct。

**题目：红黑树是有序的吗？他的顺序或者排序是怎么样的？**

+ **红黑树是有序的**，因为它是二叉搜索树，满足左小右大的键不变式。
+ **排序结果由比较规则决定**，中序遍历输出就是从小到大的序列。
+ 旋转只为平衡高度，**不会改变中序顺序**；重复键的处理则取决于具体实现策略。

# 1 宏与结构体相关
## 1.1 问题
+ 这里为什么要用 define 而不是 typedef
+ 为什么要用 RBTREE_ENTRY
+ 其中 name 与 type 代表什么

## 1.2 回答
+ **define 的作用是参数化生成代码**，相当于在 C 里模拟“带参数的类型模板”。`typedef` 不能带参数，无法根据不同节点类型自动生成 `left/right/parent` 指针类型。
+ **RBTREE_ENTRY 用于复用红黑树链接域布局**，把 `left/right/parent/color` 这一套固定字段抽出来，避免复制粘贴与类型写错。
+ `type` 决定指针指向的节点类型，例如生成 `struct rb_node *left`。
+ `name` 是生成的 `struct name { ... }` 的标签名。为空时可生成匿名 struct，常用于只需要成员而不需要类型名的场景。

# 2 红黑树基础概念
## 2.1 问题
+ 红黑树是什么
+ 作用和应用场景怎么样

## 2.2 回答
+ 红黑树是**自平衡二叉搜索树**。二叉搜索树保证有序，红黑规则限制高度，保证最坏时间复杂度。
+ 典型性质要点
    - 节点非红即黑
    - 根为黑
    - NULL 或 NIL 视为黑
    - 红节点不能有红孩子
    - 从任意节点到其所有后代 NIL 的路径上黑节点数一致
+ 作用
    - **有序查找与范围能力**
    - **最坏 O(log N) 的稳定性能**
+ 应用
    - 有序 map set
    - 内核与系统软件中的对象索引与区间结构
    - 时间线与事件管理
    - 内存索引结构

+ 红黑树是有序的吗
+ 顺序或者排序是怎么样的

## 4.2 回答
+ **红黑树是有序的**，因为它是二叉搜索树

# 8 为什么需要红节点与黑节点
## 8.1 问题
+ 为什么需要红节点和黑节点

## 8.2 回答
+ 颜色是平衡约束的低成本元数据
+ 黑节点保证黑高一致，相当于硬约束
+ 红节点提供弹性，但不允许连续红防止退化
+ 插入默认红是为了避免立即破坏黑高

# 9 根节点是否为黑
## 9.1 问题
+ 根节点一般都是黑的吗

## 9.2 回答
+ **通常规定根必须为黑**
+ 插入修复中可能把祖父染红并上移，最终会统一把根强制染黑
+ 根黑使证明与实现更简单，减少边界特判

# 10 插入修复代码细节
## 10.1 问题
+ 插入默认红
+ 代码里 `z = z->parent->parent` 有什么意思

## 10.2 回答
这句出现在父红叔红分支中，其含义是

+ 变色后祖父被染红
+ 祖父与其父节点可能形成新的红红冲突
+ 因此把修复焦点从当前 z 上移到祖父继续 while 循环

示意

变色前

```plain
gB
     /  \
   pR   yR
   /
  zR
```

变色后

```plain
gR   可能与更上层冲突
     /  \
   pB   yB
   /
  zR
```

所以需要

+ `z = g`
+ 再检查 `g->parent` 是否为红

# 11 插入算法全流程
## 11.1 问题
+ 能否详细讲解红黑树的插入

## 11.2 回答
插入分两段

+ 按二叉搜索树规则插入，默认新节点红
+ 当父为红时循环修复

修复分两类由叔叔颜色决定

父红叔红

+ 父与叔变黑
+ 祖父变红
+ z 上移到祖父继续修复

父红叔黑

+ 分四种形态
    - 左左 左右 右右 右左
+ 折线形先对父旋转转为直线形
+ 直线形对祖父旋转
+ 配合变色一次性消除冲突

插入结束

+ 根强制变黑

# 12 旋转会不会破坏有序性
## 12.1 问题
+ 旋转会不会破坏红黑树的有序性

## 12.2 回答
+ **不会**，原因是旋转保持中序序列不变
+ 左旋前后中序序列一致
    - α x β y γ
+ 只有两种情况下会破坏
    - 原树本身不满足二叉搜索树不变式
    - 旋转指针更新实现错误

# 13 epoll 事件管理与红黑树使用
## 13.1 问题
+ epoll 事件块管理如何实现
+ 红黑树如何使用

## 13.2 回答
epoll 内部可以抽象为两张表

+ 关注表
    - 存储所有被 epoll_ctl ADD 的 fd 条目
    - 需要查重、查找、修改、删除稳定
    - 采用红黑树，典型复杂度 O(log N)
+ 就绪表
    - 存储当前已就绪的条目
    - 需要 O(1) 入队与批量取出
    - 采用链表

事件流转闭环

1. epoll_ctl ADD
    1. 创建 epitem
    2. 插入红黑树
    3. 将回调挂到目标文件等待队列
2. fd 状态变化
    1. 驱动唤醒等待队列
    2. epoll 回调执行
    3. epitem 加入就绪链表
    4. 唤醒 epoll_wait
3. epoll_wait
    1. 从就绪链表取出
    2. poll 复核事件
    3. 返回用户态

关键结论

+ **红黑树用于管理与定位条目**
+ **事件到来依赖等待队列回调，不依赖红黑树**

结构关系示意图

```plain
epoll 实例 eventpoll
        ┌─────────────────────────┐
        │ 关注表 红黑树 rbr        │  查找 修改 删除 O(logN)
        │   ┌───────────────┐     │
epitem──┼──▶│ rb_node 嵌入   │     │
        │   └───────────────┘     │
        │ 就绪表 链表 rdllist      │  入队出队 O(1)
        │   ┌───────────────┐     │
epitem──┼──▶│ list_head 嵌入 │     │
        │   └───────────────┘     │
        └─────────────────────────┘

目标 fd 的等待队列 wakeup
        └──回调把 epitem 放入就绪链表并唤醒 epoll_wait
```

# 学习要点清单
+ 红黑树是二叉搜索树，**有序性由比较规则决定**
+ 插入默认红是为避免破坏黑高
+ 插入修复的分支判断核心看两点
    - 父是否红
    - 叔叔是否红
+ 父红叔红
    - 变色并上移
+ 父红叔黑
    - 旋转配合变色
+ 旋转保持中序序列不变，因此不破坏有序性
+ epoll 中红黑树用于关注表管理，就绪事件用链表
