# 哈希的应用学习笔记

> 日期：2026-01-22
> 主题：哈希表的核心原理与工程实践

## 1. 哈希概述
### 1.1 核心作用
- 将任意长度的数据映射为固定长度的值
- 广泛应用于散列表、布隆过滤器、分布式一致性哈希

### 1.2 哈希函数选择标准
1. **计算速度快**：如果比直接比较字符串还慢，就没有意义。
2. **强随机分布性**：这是最重要的。保证输入微小的变化能引起输出巨大的变化（雪崩效应），且映射结果在空间上均匀分布，避免“哈希聚集”。

### 1.3 常用算法
- **MurmurHash2/3**：工业界最常用，速度和质量的黄金平衡点（Redis, Java, Hadoop 都在用）。
- **SipHash**：Redis 默认使用。特点是能防止“哈希DoS攻击”（即有人故意构造大量冲突的 key 攻击服务器）。
- **CityHash**：Google 出品，专门针对字符串优化的哈希算法。

## 2. 散列表 (Hash Table)
### 2.1 基本构成
- **哈希函数**：定位器。
- **数组**：实际存数据的容器（Bucket）。
- **冲突策略**：链表法或开放寻址。

### 2.2 核心操作流程
- **插入**：`index = hash(key) % size`。若冲突，处理冲突。
- **查询**：算出 index，然后遍历冲突链表/探测序列。

### 2.3 冲突处理详解
#### 2.3.1 链地址法 (Separate Chaining) - **STL & Redis 采用**
- **结构**：数组每个位置是一个链表（或红黑树，如 Java HashMap）。
- **优点**：简单，对负载因子不敏感（>1 也能工作）。
- **缺点**：指针占用额外空间，缓存不友好（链表节点内存不连续）。

#### 2.3.2 开放寻址法 (Open Addressing) - **Python 早期 & ClickHouse 采用**
- **结构**：所有元素都存在数组里。
- **探测方式**：
    - 线性探测：`i+1, i+2...`（容易产生堆积）。
    - 二次探测：`i+1^2, i-1^2...`。
    - 双重哈希：用第二个哈希函数算步长。
- **优点**：内存连续，缓存友好，无指针开销。
- **缺点**：删除麻烦（需要标记 Deleted），负载因子高时性能急剧下降。

### 2.4 负载因子与扩容
- **定义**：`load_factor = n / m`。
- **阈值**：
    - 链地址法：通常 0.75 ~ 1.0。
    - 开放寻址法：必须 < 1，通常 0.5 就得扩容。
- **扩容代价**：分配新数组 + Rehash（所有元素重新计算位置）。

## 3. 工程实现细节深入

### 3.1 SipHash：防御哈希DoS攻击
- **背景**：传统哈希函数可能被攻击者利用，构造大量冲突的Key导致性能退化。
- **实现**：哈希函数中加入只有服务器知道的随机密钥 `secret_key`。
- **效果**：攻击者无法预测哪些Key会冲突，从而防止故意构造冲突的攻击。

### 3.2 开放寻址法的删除陷阱
- **问题**：删除节点时不能直接清空，否则会破坏线性探测的查找路径。
- **解决方案**：使用 **Deleted 标记**，让探测过程能够继续。
- **示例**：A[0] B[1] C[3] D[6]，删除C后若清空[3]，D将无法被找到。

### 3.3 STL unordered_map 的全局链表优化
- **传统链地址法**：每个桶是一个独立链表，遍历需扫描整个数组。
- **STL优化**：每个节点额外维护一个全局链表指针，用于迭代器遍历。
- **结构**：
  ```cpp
  struct hash_node {
      Key key;
      Value value;
      hash_node* next_in_bucket;  // 桶内链表
      hash_node* next_in_global;   // 全局遍历链表
  };
  ```
- **优势**：迭代器遍历的时间复杂度从 O(桶数量) 优化到 O(元素数量)。

## 4. 布隆过滤器深度解析

### 4.1 核心思想：存储"指纹"而非"本身"
- **传统哈希表**：存储完整的 Key 和 Value
- **布隆过滤器**：只存储 Key 的指纹（多个哈希函数的位标记）

### 4.2 数学基础
#### 假阳率公式
$$P = (1 - e^{-kn/m})^k$$

- **P**：假阳率（False Positive Rate）
- **k**：哈希函数个数
- **n**：预期插入元素数量  
- **m**：位数组长度

#### 最优参数计算
$$m = -\frac{n \ln P}{(\ln 2)^2} \quad k = \frac{m}{n} \ln 2$$

### 4.3 实际案例：1亿邮箱黑名单
```cpp
n = 100,000,000    // 1亿个邮箱
P = 0.001          // 0.1% 误判率

计算结果：
m ≈ 1.917 × 10^9 位 ≈ 228 MB  // 仅需228MB！
k ≈ 10 个哈希函数
```

### 4.4 关键特性
#### 不能删除的原因
- 多个Key可能共享比特位
- 删除会误伤其他Key的判断结果

#### 必然的误判性
- 位数组逐渐填满时，随机碰撞概率增加
- 通过数学计算将误判率控制在可接受范围内

#### 工程权衡
- **内存 vs 准确性**：位数组越大，误判率越低
- **哈希函数数量**：过多过少都会影响误判率

### 4.5 应用场景
- **缓存穿透防护**：先查布隆过滤器，不在则直接返回
- **垃圾邮件过滤**：快速判断邮件是否在黑名单
- **爬虫去重**：避免重复爬取相同URL
- **数据库查询优化**：前置过滤不存在的记录

## 5. 分布式一致性哈希

### 5.1 解决的问题
- **传统方法的灾难**：`hash(key) % N` 在增删节点时导致大规模缓存失效
- **缓存雪崩**：几乎所有请求同时涌向数据库，造成系统崩溃

### 5.2 核心思想：固定的圆环
1. **构建圆环**：0 ~ 2^32-1 的哈希空间映射为环
2. **服务器映射**：IP+Port 哈希后放到环上
3. **数据映射**：Key 哈希后放到环上
4. **查找规则**：Key 顺时针找到的第一个服务器

### 5.3 虚拟节点机制
- **问题**：物理节点少时分布不均
- **解决**：每个物理节点生成多个虚拟节点（通常 150-200 个）
- **效果**：提升分布均匀性，减少数据迁移量

### 5.4 工程实现要点
- **数据结构**：使用 `map` 或 `set` 维护有序哈希值
- **查找算法**：`lower_bound()` 找到下一个节点
- **节点管理**：新增时注册虚拟节点，删除时清理

### 5.5 性能优势
- **数据迁移最小化**：只影响相邻节点的数据
- **负载均衡**：虚拟节点保证数据均匀分布
- **高可用性**：单点故障影响范围有限

## 6. 大数据处理案例：2G内存统计最大频次整数

### 6.1 问题分析
- **限制**：2GB内存无法完全加载大文件
- **目标**：统计出现次数最多的整数

### 6.2 解决思路：哈希分流
1. **文件拆分**：将大文件分成多个小文件
2. **哈希分流**：相同整数必须落在同一文件（使用强随机分布的哈希函数）
3. **分治统计**：每个小文件用哈希表统计频次
4. **合并结果**：找出各文件中的最大值

### 6.3 关键技术点
- **哈希函数选择**：必须用 MurmurHash2 等强随机分布算法
- **避免简单取余**：防止数据分布不均
- **样本充分性**：数据量大时，哈希函数能保证负载均衡

## 7. 总结

### 7.1 哈希技术体系
- **基础层**：哈希函数设计（速度 vs 分布性）
- **数据结构层**：散列表（冲突处理、扩容策略）
- **高级应用层**：布隆过滤器、一致性哈希
- **分布式层**：负载均衡、数据迁移优化

### 7.2 工程权衡艺术
- **空间换时间**：布隆过滤器的内存优化
- **确定性换可用性**：一致性哈希的负载均衡
- **复杂度换性能**：虚拟节点、渐进式扩容
